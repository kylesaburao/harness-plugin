# ASD-STE100 Writer

[Documentation](../README.md) / Using the plugin

`write-asd-ste100` helps an assistant draft, revise, and review technical English with the
ASD-STE100 Issue 9 writing rules and a locally generated dictionary. Use it for procedures,
descriptions, documentation, comments, docstrings, release notes, and user-facing technical text.
It leaves code, identifiers, commands, paths, quotations, diagnostics, and established project
terminology unchanged.

The skill runs only when you invoke it. Its [behavioral contract](../../dist/harness/skills/write-asd-ste100/SKILL.md)
is what the assistant follows.

## Set up

After [installing the plugin](../../README.md#install), initialize the local reference bundle once
by following the [skill setup](../../dist/harness/skills/write-asd-ste100/INSTALL.md). Git does not
contain the extracted dictionary or its validation metadata. If you skip this step, the first
lookup or check reports the initialization command, and the assistant asks before it runs it.

## Data layout

Tracked in git, under the skill's `references/` directory:

- `writing-rules.md`: a summary of the 53 Issue 9 rules and eight recommendations, not the standard.
- `source-config.json`: pins the source URL, PDF hash, Issue 9 identity, page geometry, row counts,
  and expected dictionary hash.
- `software-terminology.jsonl`: a denylist of overused AI-coding-assistant words and phrases, each
  with a human alternative. See `software-terminology-schema.md`.
- `project-terminology-schema.md`: the format for a repository's own `STE_TERMS.jsonl`.

Generated by the initializer, under `~/.harness-plugin/write-asd-ste100/bundles/<config-sha256>/`:
`dictionary.jsonl`, `dictionary-validation.json`, and `manifest.json`. Codex and Claude Code share
the bundle, and a plugin version bump reuses it.

## Direct CLI use

Set `<SKILL_DIR>` to the installed skill directory shown by your harness. Lookup and checking use
only the Python 3 standard library and never touch the network.

```sh
python3 "<SKILL_DIR>/scripts/ste_lookup.py" WRITE
python3 "<SKILL_DIR>/scripts/ste_lookup.py" clean --part-of-speech v --json
python3 "<SKILL_DIR>/scripts/ste_check.py" document.md --mode descriptive
python3 "<SKILL_DIR>/scripts/ste_check.py" a.md b.md --mode procedural --terms STE_TERMS.jsonl
printf 'Use the tool.\n' | python3 "<SKILL_DIR>/scripts/ste_check.py" - --mode procedural
```

Every command validates the bundle before it reads it. A missing, incomplete, stale, or modified
bundle exits with status 2 and reports the failed condition and the initialization command.
`validate_references.py` is a standalone installation check, not a prerequisite for the other
commands.

Each `ste_check.py` run is a batch, even for one file. Paths are explicit, with no directory
traversal or globs, and `-` (standard input) is valid only as the sole input. One unreadable input
fails the whole batch with status 2. `fail` (status 1) means a file has a deterministic error;
`review` and `pass` exit with status 0. `--layers` selects vocabulary layers from `asd`,
`software`, and `project` (default: all three). Software-layer findings are `review` suggestions
and never cause a `fail`.

## Scope and claims

The checker is an aid for a writer with STE training. It cannot verify that technical meaning is
correct, infer every part of speech, find every passive construction, or resolve every technical
term. Correct technical content and established project terminology outrank a vocabulary swap.
Call text `STE-compliant` only after lexical, mechanical, and semantic review against Issue 9.

## Development

`extract_dictionary.py` and `build_dictionary.py` turn the pinned PDF into dictionary records, and
`initialize_references.py` drives acquisition, extraction, validation, and installation. Use the
extractor and builder directly only for development. Tests live in `tests/write-asd-ste100/` and
use synthetic dictionary records; see [focused checks](../development/testing.md).
