# Backup performance benchmark

The benchmark harness creates an isolated UUID-named workspace under every configured storage root, generates the same deterministic corpus in each workspace, runs every available source-to-target pairing through the real backup CLI, validates each ZIP, records its size and POSIX mode, and removes its temporary workspaces. It records unavailable hardware instead of substituting a local directory for another storage type.

Copy [`backup-manifest.example.json`](backup-manifest.example.json) to an ignored local manifest, replace the placeholder roots, and run:

```sh
node scripts/backup-benchmark.js benchmark/backup-manifest.local.json benchmark/backup-results.local.json
```

Each result records CLI wall time, child user-plus-system CPU time from `/usr/bin/time -p`, archive size, ZIP validity, and level 6 and level 9 compression trials. A Google Drive corpus generated by the harness is already hydrated, so its result is marked `generated-cached`. To characterize cold hydration, prepare and evict an equivalent provider-backed corpus before a separate run, set that location's `sourcePath` to the corpus, and label its `hydration` as `cold`. A supplied `sourcePath` is read but never removed. Do not interpret a faster repeated read as compression improvement.

CLI completion only means that the file was closed and atomically installed in the provider-backed directory. The CLI cannot prove that Google Drive finished uploading it. Google Drive results therefore contain a separate `uploadObservation` field whose completion time remains `null` until provider state is observed and recorded.
