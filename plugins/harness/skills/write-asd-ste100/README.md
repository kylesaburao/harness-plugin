# ASD-STE100 Writer skill

`write-asd-ste100` is a private skill for technical English on Codex and Claude Code. It uses the
ASD-STE100 Issue 9 writing rules and a locally generated dictionary. Git does not contain the
extracted dictionary or its validation metadata.

The skill helps an assistant draft, revise, and examine procedures, descriptions, documentation,
comments, docstrings, release notes, and user-facing technical text. It leaves code, identifiers,
commands, paths, quotations, diagnostics, and established project terminology unchanged.

`SKILL.md` is the operational contract the assistant follows. `INSTALL.md` is the one-time setup.
This file is the human overview.

## Install and initialize

The skill ships with the `harness` plugin (repository root `README.md` has the marketplace and
plugin commands). After install it has no reference data: run `initialize_references.py` once, per
`INSTALL.md`.

Initialization needs the `pypdfium2` package. macOS's system `python3` is not meant to receive
`pip install`s, so use a virtual environment:

```sh
python3 -m venv .venv
.venv/bin/pip install pypdfium2
.venv/bin/python scripts/initialize_references.py
```

Runtime lookup and checking (`ste_lookup.py`, `ste_check.py`, `validate_references.py`) use only
the Python 3 standard library and never touch the network.

The initializer downloads the pinned Issue 9 PDF, verifies its SHA-256, extracts and validates the
dictionary, then installs the bundle atomically. Options:

- `--pdf PATH` uses a local copy of the pinned PDF instead of downloading.
- `--import-from DIR` copies a valid bundle from an older install, no download or `pypdfium2`.
- `--force` rebuilds a bundle that is already valid.
- `--preflight` checks the source, configuration, and dependency without building.
- `--json` makes any run's error or success report machine-readable.

## Data layout

Tracked in git: `references/writing-rules.md` (the 53 Issue 9 rules and eight recommendations, a
summary, not the standard), `references/project-terminology-schema.md`,
`references/software-terminology-schema.md`, `references/software-terminology.jsonl`, and
`references/source-config.json` (pins the URL, PDF hash, Issue 9 identity, page geometry, row
counts, and expected dictionary hash).

Generated by the initializer, under `~/.harness-plugin/write-asd-ste100/bundles/<config-sha256>/`:
`dictionary.jsonl`, `dictionary-validation.json`, and `manifest.json`. Keying by the source-config
hash makes the location independent of plugin version and lets bundles for different configs
coexist. Codex and Claude Code share the bundle; a plugin bump reuses it.

## Runtime behavior

Every runtime command validates the bundle before reading it, in one call. Do not run a separate
readiness preflight. A missing, incomplete, stale, or modified bundle exits status 2 with a stable
code, the failed condition, the generated-data path, the initialization command, and the pinned
source identity, as plain text or, with `--json`, structured JSON. No Python traceback.

`validate_references.py` is a standalone installation check, not a prerequisite for the other
commands.

```sh
python3 scripts/ste_lookup.py WRITE
python3 scripts/ste_lookup.py clean --part-of-speech v --json
python3 scripts/ste_check.py document.md --mode descriptive --json
python3 scripts/ste_check.py a.md b.md --mode procedural --terms STE_TERMS.jsonl --json
printf 'Use the tool.\n' | python3 scripts/ste_check.py - --mode procedural --json
```

Every `ste_check.py` invocation is a batch, including one file. Paths are explicit: no directory
traversal, no globs. `-` (stdin) is valid only as the sole input. An LLM always passes `--json`.
The checker validates and reads every input before analyzing any file; one unreadable input fails
the whole batch with `input_read_failed` and status 2. `fail` (status 1) means a readable file has
a deterministic error; `review` and `pass` are status 0.

`--layers` selects vocabulary layers from `asd`, `software`, `project` (default: all three).
`--layers software` alone reviews overused-term findings without base-dictionary unknown-term
noise. The `software` layer flags overused AI-coding-assistant phrasing at `review` severity,
category `overused_term`, and never causes a `fail`.

## Terminology layers

A repository can supply `STE_TERMS.jsonl` for approved project terminology, passed with `--terms`.
See `references/project-terminology-schema.md`.

`references/software-terminology.jsonl` is a git-committed denylist of overused AI-coding-assistant
words and phrases with a human alternative for each. See `references/software-terminology-schema.md`.

## Maintenance

`extract_dictionary.py` and `build_dictionary.py` turn the pinned PDF into dictionary records;
`initialize_references.py` drives acquisition, extraction, validation, and installation. Direct
extractor or builder use is for development only.

Tests live at `tests/write-asd-ste100/` in the repository, not in the plugin install:

```sh
python3 -m unittest discover -s tests/write-asd-ste100 -v
```

They use synthetic dictionary records and do not reproduce the ASD word list. Dictionary
integration tests run only when a valid local bundle exists.

## Scope and claims

The checker is an aid for a writer with STE training. It cannot verify that technical meaning is
correct, infer every part of speech, find every passive construction, or resolve every technical
term. Correct technical content and established project terminology outrank a vocabulary swap.

Use `STE-compliant` only after lexical, mechanical, and semantic inspection confirms the text
against Issue 9. Otherwise use `STE-aligned` or `checked against the bundled Issue 9 data`.
